Benchmarks · compare the work as well as the clock

Minify++ is fast, but it is deliberately not the most aggressive compressor.

A useful minifier comparison needs at least three dimensions: elapsed time, output size and the semantic work each tool is willing to perform. Minify++ is a conservative scanner. esbuild and Lightning CSS parse more deeply and can make structural rewrites that Minify++ intentionally leaves alone.

Two benchmark layers: the Performance page owns Minify++'s repeatable in-process regression gate. This page owns cross-tool context and makes the comparability limits explicit.

CSS: same fixtures, output-size comparison

The checkpoint below ran Minify++ 1.1.0 on the GoalSmashers copies of Bootstrap 4, Animate.css 4.1.1 and Tailwind CSS. Those are the fixture names used by Lightning CSS's published benchmark. The esbuild and Lightning CSS output sizes below are the values published by Lightning CSS; Minify++ output sizes are from this checkpoint.

FixtureInputMinify++esbuildLightning CSS
Bootstrap 4200,078 B165,836 B160,332 B143,091 B
Animate.css95,374 B77,454 B72,183 B23,666 B
Tailwind CSS2,380,419 B1,973,801 B1,961,642 B1,824,130 B

On Bootstrap 4, Minify++ output is about 3.4% larger than esbuild and 15.9% larger than Lightning CSS. On Tailwind, it is only about 0.6% larger than esbuild and 8.2% larger than Lightning CSS. Animate.css exposes the architectural difference much more sharply: Minify++ preserves substantially more of the original stylesheet while Lightning CSS performs deeper typed/structural optimisation.

This is not presented as a compression victory for Minify++. It is evidence of the trade-off Minify++ actually makes: remove lexical redundancy cheaply and conservatively, but do not chase every AST-level rewrite available to a dedicated CSS compiler.

Minify++ timing on those fixtures

Using the Minify++ C++ API in-process, compiled with g++ 14.2.0 -O2 on the Linux 6.18.35 x86-64 checkpoint host, with five warmups and 45 measured runs:

Bootstrap 41.156 ms165.0 MiB/s

No fake speed leaderboard. Lightning CSS publishes esbuild and Lightning CSS timings for these fixtures, but those measurements were produced in a different environment and through JavaScript APIs. This page does not divide those times into the local Minify++ timings and call the result a speedup. The repository includes a same-host CLI harness for running all three binaries together.

Reproduce a same-host CSS comparison

python3 benchmarks/compare_css_tools.py \
  --minifypp ./minify \
  --esbuild /path/to/esbuild \
  --lightningcss /path/to/lightningcss \
  bootstrap-4.css animate.css tailwind.css

The CLI harness reports median wall-clock time and output bytes on exactly the same files. Keep those results separate from in-process API benchmarks because process startup is part of the measurement.

JavaScript: preparing Nift for the minifier showdown

The privatenumber JavaScript minification benchmark is a useful external target because it runs each minifier in its own process, checks artifact integrity before and after minification, measures minified and gzip size, and averages five timing runs. The Minify++ repository now carries a reference Nift adapter matching that benchmark's adapter model.

Nift uses the same Minify++ engine for nift minify. A local integration probe on a 515,136-byte real ES-module bundle produced byte-identical output through standalone Minify++ and Nift: 341,584 bytes, or 102,233 bytes with gzip -9. The median five-run CLI timings were 19.5 ms for standalone Minify++ and 16.6 ms for Nift on that probe; the small reversal is normal process/noise territory, not evidence that the wrapper is faster than its engine.

No upstream Nift rank is published yet. A meaningful result needs an actual run of the upstream suite against its exact current artifacts and competitors. The adapter is ready for that run; until it happens, the website will not splice a local Nift measurement into someone else's leaderboard.

What the results say

  • Speed is a genuine Minify++ strength, especially for conservative whole-buffer scanning.
  • Compression is intentionally less aggressive. Dedicated parsers such as Lightning CSS can win substantially on stylesheets with structural optimisation opportunities.
  • Output bytes alone are not semantic evidence. Smaller is useful only after the transformation contract is trusted.
  • Benchmark methodology is part of the result. In-process throughput, CLI latency and cross-host published numbers answer different questions.

That is why Minify++ keeps semantic evidence ahead of benchmark marketing: speed is useful only after correctness survives the contract.
